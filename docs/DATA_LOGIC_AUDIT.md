# 数据逻辑审计与统计口径

> 本文记录 2026-11-02 的审计与当时实现。2026-11-04 已按运维反馈调整扫描结果显示、停止输出旧估算并增加自动清理；当前行为以 [扫描结果显示与统计清理](SCAN_RESULT_DISPLAY.md) 为准。原始采样的新鲜度继续用于自动操作与通知保护。

审计日期：2026-11-02。本文覆盖 AntMonitor 场地端与 AntMonitor Cloud 的采集、实时汇总、客户报表、归档、跨场地合计、日报及相关告警逻辑。

本轮通过源码审查、隔离 SQLite 数据库、模拟设备/网络响应和真实前端函数回归，确认并修复了多处可复现的数据逻辑问题。**没有访问用户生产数据库、矿机、集装箱控制器或运行中的云端服务。** 下列数值是测试输入及其计算结果，不是对某个生产场地账单的结论，也不表示已经证明所有设备和场景都没有问题。

## 1. 先明确页面上的数值

### 算力、平均算力与累计交付

| 指标 | 含义 | 例子 |
| --- | --- | --- |
| 实时算力，TH/s、PH/s、EH/s | 当前有效采样中的计算速率；客户值为该客户各台机器实测速率之和 | 一台当前 300 TH/s、另一台 290 TH/s，客户当前为 590 TH/s |
| 近 24 小时平均算力 | 对实际采样记录按有效持续时间加权，仍是速率 | 293 TH/s 稳定运行完整一天，平均仍为 293 TH/s |
| 累计交付，TH·h、PH·h、EH·h | 速率乘以小时数后的累计量 | 293 TH/s 持续 24 小时，累计为 7,032 TH·h |
| 当前功率，固定 kW | 当前有效矿机功率读数的合计 | 3,000 W 在网页显示为 3 kW |
| 估算耗电，固定 kWh（度） | 有效功率读数随时间的积分 | 3,000 W 持续 1 小时，估算为 3 kWh，即 3 度 |
| 固件平均 | 矿机固件返回的平均值 | 周期由固件定义，不保证是本系统近 24 小时平均 |

`1 PH/s = 1,000 TH/s`，`1 EH/s = 1,000,000 TH/s`。因此，大场地出现 PH/s、EH/s 可以是正常的单位换算；原先客户列中的 `EH·h` 是累计交付，不应该解释为一天的平均算力。

`台数 × 标称算力` 是理论容量。真实客户实时值需要加总当前实测值；真实周期平均还会受到停机、降频、波动、机器归属变化及缺测的影响。

### 当前功率与统计期耗电的固定显示单位

两端网页的**当前功率固定显示 kW**，**累计耗电固定显示 kWh（度）**，不再随数值大小切换成 MW、MWh。`kW` 是当前负荷，`kWh` 是一段时间累计的电量：1,000 kW 持续 1 小时对应 1,000 kWh。数学换算仍为 `1 MW = 1,000 kW`、`1 MWh = 1,000 kWh`，显示单位统一不改变底层数值。

设备原始值和 API 仍按字段约定使用单位，例如单机 `power_w` 为 W，摘要 `total_power_kw / power_kw` 为 kW，报表 `power_kwh` 为 kWh。不能因为网页固定显示 kW，就把原始 W 字段再当成 kW 加总。

总览的功率是**矿机当前功率读数合计**。它不证明已经覆盖外部冷却设备、配电回路或损耗，也不等于全场电表负荷。AntBox 两路配电读数单独展示，不加到矿机功率总量里，避免把可能重叠的回路重复计算。全场实际负荷和结算电量需要用覆盖相应回路的电表核对。

### 零值、离线与未知

- **实测为零**：设备明确返回有效的 0；保留为 0。
- **监控确认离线**：本系统在算力交付和功率估算中按 0 贡献处理。这是监控估算约定，不能据此断言设备已经断电、待机功耗为零或网络隔离的矿机没有继续挖矿。
- **未知、缺测、过期**：没有足够证据确认当前值，不自动填 0，也不无限沿用上次读数。界面显示未知、已知部分或覆盖不足。

**耗电始终是监控估算；正式电费结算和物理耗电核验需要电表。**

## 2. 数据从哪里来，在哪里判定有效

1. 设备驱动解析单机字段和实际读取时间，保留可验证的测量值。
2. 场地数据库保存原始快照和 `measured_ts`；当前 API、告警和自动动作使用另一个经过新鲜度检查的视图。
3. 客户历史报表按时间区间、当时的客户归属和每项指标的有效性积分；小时归档保存这些积分及覆盖信息。
4. 云端检查摘要完整性、源扫描时间、源发送时间及最早实际测量时间；成功收到 HTTP 请求本身不证明里面的矿机数据新鲜。
5. 云端在满足各指标条件时生成全网合计、同窗客户合计和按 UTC+8 切日的日报；通知使用相同的有效性规则。

### 采集侧修复与证据

| 输入或场景 | 原问题 | 本轮处理及复现结果 |
| --- | --- | --- |
| UniPlus `hr_realtime=293000`，但 `chip_temp=["bad"]` | 坏的可选温度字段可能让整台机器变成 offline | 保留 online 和 293 TH/s；无效温度、运行时长等可选值为未知 |
| 算力 `-293000`、固件平均 `true`、功率 `-6000` | 负值、布尔值可能进入数值统计 | 这些输入为未知；合法数字 0 保留 |
| cgminer `MHS 5s=293000000`、`MHS av=291000000` | 单位及实时/平均字段需要分开核验 | fixture 分别得到 293、291 TH/s；只有平均字段时不冒充实时读数 |
| 先读到 293 TH/s，再发现空 IP，整轮多花 1,800 秒 | 整轮完成时间把早先读数刷新为“刚采到” | 原始读数和原 `measured_ts` 保留，当前视图、告警和自动动作将过期记录视为 unknown |
| 首扫 5 个地址，实际只发现 2 台机器 | 空地址被当成离线矿机，抬高总台数 | 只保留名册中的机器和明确发现的在线新机；已知机器的 unknown 仍计入名册总数 |
| 解析或程序异常 | 异常可能被解释成“已确认离线” | 异常状态为 unknown，避免伪造离线证据 |

单机测量正常有效期为 **900 秒**。历史区间还受下一轮快照、请求边界及对应原采样时间加 900 秒限制。旧记录没有 `measured_ts` 时，只能用旧扫描时间作为兼容估计；升级不能创造过去没有记录的精确采样时间。

这是按轮次快照估算的统计模型。它不会把所有机器重建成逐秒事件流，也不能测出两次采样之间未被观察到的瞬时停机。

## 3. 实时汇总需要能对账

同一份当前数据用于场地总览、公开只读 API、矿机列表、客户/矿工分组和货架汇总。对应指标需要全部相关机器有效时，才输出完整总量。

例如，2 台已知机器中，一台有效为 293 TH/s，另一台 unknown：

- 名册总数仍为 2，已知在线为 1，unknown 为 1。
- 完整总算力为未知，已知算力小计为 293 TH/s。
- 不能显示完整总算力 293 TH/s，也不能把另一台算成确认离线。
- 功率是否完整单独判断，不能因为算力完整就认定功率完整。

全场能效按 **总瓦数 / 总 TH/s** 计算。例如 100 TH/s、2,000 W 与 300 TH/s、12,000 W 两台机器，能效为 `14000 / 400 = 35 J/TH`；对 20 与 40 J/TH 直接取平均得到的 30 J/TH 不代表这两台机器的总体能效。

当前每台平均算力的分母是当前在线机器数；它与客户近 24 小时平均是不同的指标。没有有效在线机器或数据不完整时，不补出一个零均值。

## 4. 客户历史统计的统一公式

对每一个有效区间 `i`，令客户总算力为 `H_i`（TH/s），总功率为 `P_i`（W），实际有效持续时间为 `Δt_i`（秒）：

```text
观测平均算力 = Σ(H_i × Δt_i) / ΣΔt_i
累计交付 TH·h = Σ(H_i × Δt_i) / 3600
估算耗电 kWh = Σ(P_i × Δt_i) / (1000 × 3600)
在线率 = Σ(在线机器数_i × Δt_i) / Σ(已知状态机器数_i × Δt_i)
各指标覆盖率 = 该指标有效观测秒数 / 请求窗口秒数
```

公式中的有效区间按指标独立选择。某客户的相关机器中有一台缺少功率，本区间的完整客户功率就未知；算力和状态仍可能有效。状态 unknown 不等于 offline。在线率仅使用已知状态的机器时间，并同时显示状态覆盖，避免“仅观测 5 分钟在线，却看起来全天 100% 在线”。

在线率分母随机器数量变化，不能替换为扫描次数，也不能对每台机器的百分比直接取平均。例：前半小时只有一台在线，后半小时增加一台离线机器，则在线机器时间为 3,600 秒，已知机器时间为 5,400 秒，在线率为 **66.67%**。

### 已复现的历史统计错误

以下默认功率为 3,000 W，单机算力为 300 TH/s；特别标明的场景除外。

| 场景 | 原结果或错误 | 修复后的结果 |
| --- | --- | --- |
| 同一机器前 30 分钟属于 A，后 30 分钟属于 B | 把整小时的 300 TH·h、3 kWh 全部归给 B | A、B 各 150 TH·h、1.5 kWh；归档前后相同 |

| 第一条有效记录晚 5 分钟出现 | 反向补满整个小时 | 只覆盖 55 分钟，得到 275 TH·h、2.75 kWh |
| 只有完整 manual 扫描 | 平均算力有值，旧累计字段却为零 | manual 与 full、quick 使用同一积分规则，完整小时为 300 TH·h、3 kWh |

| 换 IP 前后记录两个地址，但同一时刻仅一台 | IP 并集被称作“峰值 2 台” | 已观测同时峰值为 1；身份迁移仍受既有 IP、SN、MAC 识别能力限制 |

| manual 数据已归档且 raw 被清理 | 只查旧账本，误提示没有历史 | 历史跨度提示同时检查 v2 与算力归档；真正有效覆盖仍以每项字段为准 |

客户归属只按时间向前继承。当前名册或未来一次读到的 worker 不能倒填过去。下架用 `kind="inventory"` 的快照事件表达，保留剩余机器原来的测量时间；同一秒多个事件按扫描 ID 顺序生效。

## 5. 跨场地合计必须使用相同的真实窗口

本地客户接口和上报默认使用共同的 UTC 十分钟边界：

```text
period_end = floor(now / 600) × 600
period_start = period_end - requested_hours × 3600
```

`period_start_ts / period_end_ts` 描述算力平均窗口；`billing_period_start_ts / billing_period_end_ts` 描述交付、功率、在线状态窗口。程序实际查询这个区间，不能只给一个旧滚动报表贴上新时间标签。明确传入的 `until_ts` 必须是合法且已经过去的 Unix 秒数。

十分钟对齐后，报表截止可能比现在早几分钟；**实时列仍表示最新有效采样**。因此，当前算力与周期平均不需要完全相同。固定边界也不意味着两个场地总能在同一秒上传完毕；短暂出现窗口未对齐是如实披露，不能强行相加。

跨场地规则：

- 实时合计需要每个参与场地的读数有效、新鲜且测量时间可验证。一个场地 300 TH/s 已过期，另一个场地当前 200 TH/s，只能给出可信场地小计 200，完整合计为未知。
- 周期平均需要各场地实际起止时间相同、窗口长度相同、覆盖完整且报表未过期。两份均为“24h”的报表，截止相差 10 分钟，仍是不同窗口。
- 功率、交付使用自己的窗口和覆盖规则，不能借算力覆盖证明能耗完整。
- 一个场地均值 293 TH/s、另一个也是 293 TH/s，但窗口不齐时，586 TH/s 不能成为同窗合计平均；诊断字段保留的算术和不能作为主值。
- 两份 120 kWh 报表窗口不齐时，240 kWh 也不能作为同窗完整耗电。已有小计只表示已收到的数据，不能替代完整结果。
- 全网在线分子和总机器分母使用相同的可信场地集合，防止拿部分场地在线台数除以全部场地名册数。
- “客户数”按唯一 worker 名统计，同一 worker 出现在两个场地时客户数为 1，客户—场地关系数为 2。它依赖 worker 身份命名规则，不是对真实工商客户的自动去重。
- 各场地历史峰值之和不等于所有场地在同一时刻的峰值，网页按“各场地峰值之和”标明。

本地报表不再把 2.9 小时的保留跨度先取整成 2 小时再查询。fixture 中 293 TH/s、3 kW 运行 2.9 小时，24 小时请求应得到 849.7 TH·h、8.7 kWh，并明确只有 2.9/24 小时覆盖；本地、公开 API 与上报使用相同窗口。

### 客户历史通道也需要防止迟到覆盖

场地摘要与客户历史报表是两个独立通道，不能只给实时摘要做时间排序。云端按场地记录最近接纳的算力、计费两组真实窗口端点；旧窗口报表不能覆盖较新的报表。场地已经使用新窗口协议后，缺少窗口证据的旧报表也不能把新数据覆盖掉。

空列表同样需要时间证据。合法、较新的空报表可以清空该场地的客户历史表；延迟的旧空列表不能被误认为“现在没有客户”。空报表的窗口来自本地实际查询，不能由云端按接收时间临时补造。

### 源时间与传输延迟

云端分别保存接收时间、原始源扫描时间 `source_scan_ts` 和源发送时间 `source_sent_ts`。新鲜度判断不会把一个旧包用新的接收时间刷新。

- 一小时前生成的包，即使里面 `scan_age_s=0`，一小时后到达也不能当作刚扫描。
- 最早单机测量及每客户测量时间保留相对整轮的年龄；重复上传同一读数不能延长原测量的 900 秒有效期。
- 源时间比云端未来超过 60 秒时，不把它认定为可信的当前测量时间。
- 源扫描时间或归一后的扫描时间倒退时，旧包不能覆盖较新的场地摘要、客户实时数据或场地名称。
- 大幅时钟回拨、明显延迟和无效时间字段可能导致当前数据未知或旧包被拒绝；不是一律把它们重新标成现在。
- 缺少时间证据的旧协议与新协议明确报告未知分开处理，防止把未知重新包装成“旧版兼容的有效值”。

**场地端和云端都需要正确的系统时钟。这里做的是保守校验与防止读数变新，并非自动纠正任意时钟偏差。** 如果校时发生了回拨，后续接纳还要满足时间顺序规则，不能承诺刷新页面即可立即恢复完整合计。

## 6. 云端日报、趋势与通知共用可信时间区间

日报按 **UTC+8 的自然日** 切分。今天的覆盖分母是今天已经经过的时间；已结束日期的分母为 24 小时。网页趋势和报表截止时间通常按浏览器本地时区显示，可能与 UTC+8 日报日期边界不同；底层 Unix 秒没有因此改变。

云端摘要积分采用左值保持；单条摘要最多代表 300 秒。下一条摘要、失败响应、请求/当前时刻、午夜、扫描失效以及最早实际测量时间加 900 秒都会截断区间。算力、功率和机器状态分别记录有效时长。

| 输入 | 原问题 | 修复后 |

| 刚收到首个 360 kW 点，时间尚未经过 | 固定按一分钟记入 6 kWh | 无有效持续时间时能耗未知；5 秒后为 0.5 kWh |
| 午夜前后各观测 10 秒，功率 360 kW | 两天各被计入 6 kWh，峰值也可能跨日 | 两天各 1 kWh；昨天峰值 100 TH/s、今天峰值 900 TH/s 各归本日 |
| 360 kW 读数在第 60 秒遭遇失败，直到第 300 秒才恢复 | 桥接失败缺口，记入 30 kWh | 只确认前 60 秒，得到 6 kWh；功率覆盖 20% |
| 已经一小时前停止扫描，却每分钟重复推送一小时 | 把重复陈旧快照计为约 366 kWh | 有效覆盖 0，平均算力和能耗未知 |
| 只有一条有效 360 kW 摘要，之后 10 分钟无报告 | 一直延伸旧值 | 最多代表 300 秒，30 kWh，覆盖 50% |
| 同一接收秒写入 100、300 kW 两条快照，之后 60 秒结束 | 同一时刻可能重复加权 | 采用该秒最后一条，均值 300 kW，能耗 5 kWh |
| 程序在早晨停止，两天后查询原日报 | 当时的覆盖分母被冻结，继续显示 100% | 已结束日按 24 小时重新计算覆盖，原有能耗不被扩算成全天 |

趋势以真实时间为横轴。未知点和长期无上报区间保留断线，不转换成 0，也不跨缺口连成平稳曲线。旧口径趋势通过 `legacy_*` 单独显示虚线，不能混成已验证的新数据。

通知规则也使用有效性证据：

- 不完整或过期的机器数，既不能触发“全部掉线”，也不能消除正在持续的掉线告警。
- 算力骤降的基线和当前平均使用可信时间区间；缺测不补成零跌幅。
- “监控停滞多久”包含接收后继续经过的时间，不能永远停在包内旧的 `scan_age_s`。
- 场地失联、数据过期和真实的零算力是不同状态，页面与通知分别表达。

## 7. 份额计数与 AntBox 故障不能把缺测解释成恢复

### 矿池接受/拒绝份额

拒绝率使用可比较计数区间的新增拒绝数，除以新增接受数与新增拒绝数之和。累计计数的来源改变时必须重建基准。

已复现：池 A 活跃时累计为 1,000/0，池 B 非活跃时保留历史 10,000/1,000；仅切换活跃池，没有产生新份额，旧逻辑却把历史差额当成约 10% 拒绝率。本轮以活跃池集合身份和逐池计数检测基准变化；活跃池切换、任一池计数回退、运行时长回退或任一计数字段缺失时重建基准，不跨这些边界差分。

接受数或拒绝数缺一项时，拒绝率未知，不能补成“0 接受/100% 拒绝”或“0 拒绝”。计数来源标识使用不含原矿池 URL 的摘要，仅在运行状态中用于比较。

### AntBox 可达不等于测量完整

已复现：控制器最初明确报告漏液，320 秒后 HTTP 200、`ok=true`，但 `params={}`。旧逻辑把空故障列表当成恢复并清警；新的行为是可达但数据 unknown，保留上次明确故障及其原始测量时间。

- `online` 表示控制器可达；`data_status`、`data_complete` 表示当前数据是否可用、故障位是否完整，不能混用。
- `observed_fault_flags` 只包含本轮明确解析到的故障位。
- 缺失故障位不等于 false；只有明确 false 并满足现有连续确认规则才恢复。
- 缺测会打断恢复确认过程；保留的旧故障标明其观测属性，不能伪装成本轮再次测到。
- 两路配电功率只有两路都有效时才相加。fixture 的 1,000 W + 500 W = 1,500 W；一路缺失时总功率未知。
- 云端存在 `containers_unknown` 时，不把全网故障/离线计数认证为完整的零；容器名册数、未知数可另行显示。

本轮对 AntBox 功率单位的测试覆盖当前实现及模拟响应；第三方公开实现也只能作为对照，不能替代该用户设备型号、固件版本的原始响应或厂家规格验证。

## 8. API、归档及升级兼容

### 主要字段变化

| 范围 | 字段或行为 |
| --- | --- |
| 原始单机记录 | `measured_ts`；保留原始证据，过期时由当前视图转换为 unknown |
| 场地摘要 | `unknown`、`measurement_ts`、`hashrate_complete`、`power_complete`、两项 `*_known_machines`、`known_hashrate_ths`、`known_power_kw` |
| 客户实时 | `hashrate_ths`、`hashrate_ts`、`current_machines`；实时算力与周期平均分开 |
| 客户平均 | `avg_hashrate_ths`、`hashrate_hours`、`observed_hours`、`coverage_pct`、`period_start_ts`、`period_end_ts` |
| 客户积分与状态 | `delivered_th_h`、`power_kwh`、`uptime_pct`、`billing_hours`、`billing_period_start_ts`、`billing_period_end_ts` |
| 独立覆盖 | `delivery_observed_hours / delivery_coverage_pct`、`power_observed_hours / power_coverage_pct`、`uptime_observed_hours / uptime_coverage_pct` |
| 来源与旧记录 | `billing_source=observed/legacy_only/missing`；`legacy_delivered_th_h`、`legacy_power_kwh`、`legacy_uptime_pct`；本地同时返回 `billing_method=time_weighted_v2` |
| 台数 | `machines` 为已观测历史同时峰值或旧报表台数，须结合 `machines_source=observed/legacy`；`current_machines` 是另一时间口径 |
| 云端全网汇总 | `totals`、`observed_totals`、`metrics_complete`、`metric_known_sites`，不把部分场地小计伪装成完整总量 |
| 云端客户合计 | `window_alignment` 与 `billing_window_alignment` 独立；未验证、不齐窗、过期、部分覆盖有明确不可用原因 |
| 云端日报 | `method`、`elapsed_hours`、`metric_observed_hours`、`metric_coverage_pct`、`legacy_*` |
| 容器 | `data_status`、`data_complete`、`observed_fault_flags`、`last_observed_ts`、`containers_unknown` |

`billing_source=observed` 只表示存在有效观测，**不表示每个指标都有完整覆盖**。调用方仍须逐项检查值、覆盖、窗口和来源。新增 `null` 是有意的数据语义；API 消费方不得使用 `value or 0`、`value || 0` 之类的默认零替换。

本地 `/api/reports/customers`、`/api/public/customers` 与客户上报共用实际查询窗口；CSV 增加窗口、独立覆盖、来源及旧口径字段。CSV 的空白数值也不应在下游被自动解释为实测 0。

### 旧账本保留，历史不能凭空重建

- 场地端保留原 `worker_hourly`，新增独立 `customer_metrics_hourly / worker_metrics_hourly` 及归档进度。
- 云端保留原 `daily`，新观测日报写入 `daily_observed_v2`。
- 有保留 raw 的范围可以按新规则计算；没有 raw 的部分小时无法从一个小时总数恢复其内部实际分布，不能比例摊后声称精确。
- 既有独立算力归档可能保留算力积分，但不能因此补出功率和在线状态。
- 旧字段缺少完整性、源时间或单机时间证据时，不能自动认证为新口径完整观测。旧日报和旧曲线保留供比对，并标明局限。
- 升级不能修复当年已经错误换算、但原始设备响应没有保存的历史；也不能恢复已经清理掉的观测。
- 归档与清理使用独立进度，避免尚未完成新归档就删掉可重算的 raw。旧数据文件没有在本轮审计中被替换或“洗成正常”。

### 云端绑定使用完整 AMC1 接入信息

`AMC1-…` 是完整接入包，包含上报地址、上报 token；新建场地的完整包还包含场地 ID、名称、类型，以及需要时的证书信息。同一份包可在本地网页或命令界面粘贴，程序自动拆分，用户无需分别抄写地址和 token。旧版或共享包可能需要补填场地名称、类型。

源码复核确认，既有主复制流程已经生成 AMC1 完整包。本轮增强集中在**主复制入口、完整信息说明和解析预览**：

- 云端主按钮复制完整 AMC1 内容，并从实际待复制包解析出上报地址和场地信息供核对。
- 本地粘贴后自动填充，并显示将上报到的地址和场地信息；无效内容给出明确提示。
- 单独 token 的复制属于高级手动配置入口，明确说明它不含上报地址，不能单独用于一键绑定。
- 网页和命令行使用相同接入包；剪贴板自动读取不可用时，仍可用 Ctrl+V 粘贴完整内容。

这项改动帮助用户辨认完整接入信息及目标场地，不改变历史数据的统计口径。

### 建议升级顺序

1. 保存现有配置和数据库备份，使用原部署来源的一键更新或网页更新流程。
2. **先更新云端并重启云端进程**，使它能够接收、存储和显示新质量字段。
3. 再更新各场地端并重启场地进程；仅下载代码或刷新网页不能改变旧进程。
4. 确认两端系统时间正确，并等待新扫描、摘要和客户报表到达。默认摘要间隔为 60 秒、客户报表间隔为 600 秒。
5. 检查当前值、截止时间和每项覆盖。混合新旧版本期间，旧场地可能显示未验证、未知或覆盖不足；不要通过把空值补零来消除提示。

升级后不必机械地等满 24 小时才显示任何历史平均；可利用保留的有效 raw 或相应算力归档。能否显示完整 24 小时、完整能耗和状态覆盖，仍取决于相应历史证据。

## 9. 如何复现与继续核验

### 跨端对账演练（合成数据）

本轮实际运行了跨仓库演练：场地 A 模拟 **1,330 台**、场地 B 模拟 **539 台**，每台恒定 **293 TH/s、3,000 W**。每场地创建 **289 个五分钟快照**，包含首末边界，覆盖连续 24 小时；两场地各有 100 台属于同一个 shared 账户，其余机器分别属于各自场地的另一个账户。

演练使用隔离数据库和模拟发送，串联真实场地 API、`cloud_report._loop` 上报打包、云端 `/api/ingest/summary` 与 `/api/ingest/customers`，再通过 TestClient 请求 `/api/overview`、`/api/customers` 核对结果。它验证的是跨层计算与协议一致性，没有连接生产设备或外部云端。

| 核对项 | 计算与结果 |
| --- | --- |
| 总机器数 | 1,330 + 539 = **1,869 台** |
| 总实时与完整 24h 平均算力 | 1,869 × 293 = **547,617 TH/s = 547.617 PH/s** |
| 总功率 | 1,869 × 3 = **5,607 kW** |
| 完整 24h 估算耗电 | 5,607 × 24 = **134,568 kWh（度）**；相当于 134.568 MWh，网页固定显示 kWh |
| 客户身份数 | **3 个唯一账户、4 个场地—账户组合** |
| shared 跨场地算力 | 2 × 100 × 293 = **58,600 TH/s** |
| shared 完整 24h 耗电 | 2 × 100 × 3 × 24 = **14,400 kWh** |

随后让 A 的当前读数过期，B 继续有效：

- 完整全网当前算力为 `null`；B 的可信场地小计仍为 **157,927 TH/s**。
- shared 当前完整合计为 `null`，可信小计为 B 的 **29,300 TH/s**。
- 已经收到且仍有效的同窗完整 24h 历史均值保持 **58,600 TH/s**。当前缺测不能把真实的既往平均改成零。
- 延迟重发 A 的旧摘要被拒绝，不能用旧的正常值覆盖新的未知状态。

这些结果来自合成数据，**不是生产账本核验，也不构成性能或容量承诺**。

可复现脚本为 [cross_repository_audit.py](https://github.com/raphael2025/antmonitor-cloud/blob/main/tests/cross_repository_audit.py)。把下面的仓库路径替换为实际路径，在同一个已安装两仓测试依赖的 Python 环境中依次运行；site、cloud 必须是两个独立进程，避免两仓同名模块混用：

```bash
ANT_SITE=/path/to/antmonitor
ANT_CLOUD=/path/to/antmonitor-cloud
ANT_PAYLOAD=/tmp/antmonitor-audit-payload.json
python "$ANT_CLOUD/tests/cross_repository_audit.py" site --site "$ANT_SITE" --cloud "$ANT_CLOUD" --payload "$ANT_PAYLOAD"
python "$ANT_CLOUD/tests/cross_repository_audit.py" cloud --site "$ANT_SITE" --cloud "$ANT_CLOUD" --payload "$ANT_PAYLOAD"
```

`--payload` 指向本次演练使用的临时 JSON 文件，供第二个进程读取第一个进程生成的上报包。最终协议版本已完成这条跨端链路验证；脚本保留用于后续复跑，断言覆盖上述完整数据、当前过期及旧包迟到场景。

### 仍需要生产证据才能回答的问题

本轮没有读取生产数据，因此下面这些事项尚不能直接下结论：

- 某个矿机型号和固件版本实际返回的算力、功率单位，字段是否在特殊模式下改变；需脱敏原始响应和对应版本信息。
- 某台 AntBox 的两路功率究竟对应哪些电路、是否含冷却设备、倍率及精度；需该控制器的原始响应、规格或电表对照。
- 用户截图中的某日数据到底相差多少、缺口发生在哪一时刻；需保留原始快照的只读数据库副本和对应采样日志。
- 历史网络离线期间机器是否仍在挖矿或耗电；监控不能替代矿池侧证据及电表记录。
- 特定场地换 IP、换矿池 worker、设备替换后的实际客户归属是否正确；需真实名册、SN/MAC 及变更时间。
- 特殊长扫描耗时、时钟调整、长期离线、不同部署模式下的运行表现；模拟测试能够验证算法边界，不能替代现场连续观察。

提供核验材料时应移除密码、上报 token、矿池凭据等秘密，保留必要的字段、单位、时间及设备版本。只有取得这些证据后，才能评价某个生产报表或账期的真实误差。
